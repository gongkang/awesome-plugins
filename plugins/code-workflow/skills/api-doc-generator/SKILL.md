# API 接口实现文档生成器

分析项目代码，为每个接口生成独立的实现文档。文档作为接口行为的权威记录，供 E2E 测试、代码审查、新人 onboarding 使用。

## 何时使用

用户要求生成接口文档 / API 文档 / 接口实现文档 / 梳理接口时使用。

## 核心工作流

```
1. 探索项目结构 → 2. 扫描接口清单 → 3. 并行子代理生成文档 → 4. 验证文档质量 → 5. 输出汇总
```

### 步骤 1: 探索项目结构

**不同项目技术栈差异很大，必须先探索确定。**

探索步骤：

1. **识别技术栈**：检查项目根目录，寻找特征文件
   - Node.js: `package.json`、`tsconfig.json`、`nest-cli.json`
   - Python: `requirements.txt`、`pyproject.toml`、`setup.py`
   - Java: `pom.xml`、`build.gradle`
   - Go: `go.mod`
   - PHP: `composer.json`
   - Rust: `Cargo.toml`

2. **确定路由定义方式**：根据技术栈扫描路由注册模式
   - Node.js/Express: `app.get/post`、`router.get/post`
   - Node.js/NestJS: `@Get/@Post` 装饰器
   - Python/FastAPI: `@app.get/post`、`@router.get/post`
   - Python/Flask: `@app.route`、`@blueprint.route`
   - Java/Spring: `@GetMapping`、`@PostMapping`、`@RequestMapping`
   - Go/Gin: `r.GET/POST`、`group.GET/POST`

3. **确认项目根目录**：找到包含主要源码的目录（如 `src/`、`app/`、`cmd/`、`internal/`）

### 步骤 2: 扫描接口清单

根据步骤 1 确定的技术栈，使用 `grep` 扫描所有路由定义。

整理出接口清单，每个接口包含：

| 字段 | 说明 |
| --- | --- |
| 路由路径 | 如 `/api/v1/search` |
| HTTP 方法 | GET/POST/PUT/DELETE |
| 入口文件 | 定义路由的文件路径 |
| 入口函数 | 处理请求的函数名 |
| 所属模块 | 根据文件路径推断的模块名 |

### 步骤 2.5: 识别复杂多场景接口

扫描入口函数时必须判断接口复杂度。出现以下任一情况，标记为“复杂多场景接口”：

- 一个路由通过 `scene`、`type`、`action` 或其他场景/类型字段分派到不同策略。
- Controller 或 Service 中存在 `switch` / 多段 `if else` 分支，且不同分支的数据源/候选集、过滤、排序、分页或降级路径不同。
- 一个接口承接 3 个以上业务场景，或场景常量分散在多个 service/retrieval 文件中。
- 文档中只写“根据 scene 分派”会丢失核心逻辑。

复杂多场景接口不能只生成一个粗略流程图。文档必须包含：

1. **公共前置链路**：解析、参数校验、实验/header、用户上下文、配置开关、公共日志指标等。
2. **场景分发表**：列出源码识别到的每个 scene/type/action、触发条件、入口函数、数据源/候选集、是否分页、是否有独立降级。
3. **全局总流程图**：只描述入口到分派、公共后处理和响应，不替代分场景细节。
4. **`## 场景实现明细`**：每个主要场景单独成节；如果分支逻辑明显不同，每个场景必须有自己的流程图、数据源/候选集、过滤规则、关键配置、返回和风险。
5. **公共后置链路**：分页、响应结构、消息队列/事件/埋点、缓存写入等。

技能正文必须保持项目无关。不要在技能中写入某个项目的具体路由名、scene 名、业务常量或接口定义；示例只能使用占位符，例如 `/api/{resource}`、`scene_a`、`scene_b`、`type=x`。复杂接口的判断依据来自当前项目源码，而不是技能内固定示例。

通用例子：如果某接口按 `scene_a`、`scene_b`、`scene_c` 分派，且不同分支的数据源/候选集、过滤、排序、分页或降级差异很大，应生成“总览 + 分场景实现明细”，不能把它们压缩成“按 scene 分派后返回结果”。

### 步骤 3: 并行子代理生成文档

**核心步骤。** 对接口清单中的每个接口，启动一个子代理并行生成文档。

使用 `Agent` 工具，通过 `run_in_background: true` **一次性启动所有子代理**，不要串行等待。输出进度如 `🔄 启动 6 个并行子代理...`。

#### 子代理 prompt 模板

对每个接口，构建如下 prompt 启动子代理：

```
你是代码分析专家。请为以下接口生成实现文档。

**接口信息**:
- 路由路径: {路由路径}
- HTTP 方法: {HTTP方法}
- 入口文件: {入口文件路径}
- 入口函数: {入口函数名}
- 所属模块: {所属模块}

**输出路径**: docs/interfaces/{文件名}.md

**分析要求**:
1. **只读分析**，不修改任何代码文件
2. 阅读入口文件，理解路由注册方式
3. 深入追踪入口函数的完整调用链（内部函数、外部服务、配置依赖）
4. 识别业务规则和过滤逻辑（参数校验、归一化、条件分支、降级路径）
5. 识别可观测性（日志、监控指标、审计或埋点事件）
6. 标注已知风险和边界情况
7. 如果入口按 scene/type/action 等字段分派，必须按“复杂多场景接口”规则输出公共链路、场景分发表、总流程图和分场景实现明细；不得只写粗略大流程。

**文档结构**: 严格按照下方"文档模板"生成，每个章节必须有实际内容，不能留空表格。
```

### 步骤 4: 验证文档质量

所有子代理完成后，进行基本验证：

1. **检查文件是否存在**：确认 `docs/interfaces/` 目录下生成了对应数量的 `.md` 文件
2. **检查文档结构**：每个文档应包含所有必需章节
3. **检查表格完整性**：不应存在完全空白的表格
4. **检查复杂接口细节**：源码中存在 scene/type/action 分派的文档，必须包含 `## 场景实现明细` 或等价分场景章节；每个源码场景名应能在文档中搜索到。
5. **检查流程图粒度**：复杂接口必须至少有一个总流程图；主要场景逻辑不同的，应有对应场景流程图。禁止只用“根据 scene 分派到不同策略”概括。
6. **对比既有文档**：若项目中存在旧版详细文档，必须先对比旧文档，保留仍符合源码的详细流程、配置、风险和场景拆分，不得因为套模板删减细节。

### 步骤 5: 输出汇总

输出：生成的文档文件列表、接口总数、验证结果、发现的共性风险或值得关注的模式。

### 复杂多场景接口扩展模板

当接口被标记为复杂多场景接口时，在基础模板中增加以下内容：

````markdown
## 场景分发表

| 场景/类型 | 触发条件 | 入口函数/策略 | 数据源/候选集 | 分页 | 降级 |
| --- | --- | --- | --- | --- | --- |

## 场景实现明细

### `{scene_or_type}`

#### 触发条件与入参

说明该场景必填字段、特殊默认值、实验/header/配置开关。

#### 核心流程图

```mermaid
flowchart TD
  {该场景从分派点到返回的完整流程}
```

#### 数据源与调用链

| 数据源/候选集 | 调用函数 | 底层依赖 | 说明 |
| --- | --- | --- | --- |

#### 关键过滤、排序与补位

列出该场景独有的过滤、排序、补位、去重、状态、权限、配额、业务规则、事件和缓存逻辑。

#### 返回、降级与风险

列出该场景独有的返回字段、分页、空结果处理、降级和已知问题。
````

复杂接口的基础章节写公共逻辑，`## 场景实现明细` 写分支逻辑。不要把分支细节塞进一个过度简化的总流程图里。

## 输出

文档保存到 `docs/interfaces/` 目录，每个接口一个独立文件：

```
docs/interfaces/
├── search_category.md
├── search_first_category.md
├── prometheus.md
└── ...
```

文件名使用路由路径简化版本，规则：

- 去掉前导 `/`
- `/` 替换为 `_`
- 去掉路径参数（如 `:id`）
- 示例：`/api/v1/search/:id` → `api_v1_search_id.md`
