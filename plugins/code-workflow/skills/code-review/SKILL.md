# 代码评审

用于用户要求 review diff、代码评审或检查这次改动。默认审查全部未提交改动，静态优先，必要时少量验证。仅评审，直接在对话返回结果，不自动修复或生成报告。

## 1. 确定范围与版本

遵循用户指定的文件、目录、暂存区、提交或分支范围；未指定时使用工作区相对 HEAD 的最终状态，并纳入未忽略的新文件。

先读取适用的项目指令、Git 状态及改动清单，用 `git rev-parse --verify HEAD` 确认是否已有提交，再按文件或相关组分批读取补丁，避免一次倾倒超大 diff。下面的命令仅用于存在 HEAD 的默认范围；其他范围按表选择，没有 HEAD 时按本节的新增内容规则处理。命令在仓库根目录执行，占位符替换为已确认的引用或路径：

```bash
git status --short
git diff --no-ext-diff --no-textconv --find-renames --stat HEAD --
git diff --no-ext-diff --no-textconv --find-renames --name-status -z HEAD --
git ls-files --others --exclude-standard -z
```

默认差异是 HEAD 到工作区的净变化，不把 HEAD → 暂存区和暂存区 → 工作区两份补丁当作两个独立最终版本；同一文件可能在暂存后继续修改。未跟踪文件不在普通 diff 中，需单独读取其内容。

| 用户选择的范围 | 比较方式 | 读取评审上下文 |
| --- | --- | --- |
| 默认全部未提交 | `git diff --no-ext-diff --no-textconv --find-renames HEAD --`，另加未忽略的新文件 | 当前工作区；旧内容按 HEAD 读取 |
| 仅暂存区 | `git diff --no-ext-diff --no-textconv --cached --find-renames --` | `git show :<path>` 读取暂存内容，依赖和测试也按暂存版本核对 |
| 一个普通提交 | 确认父提交后比较 `<commit>^` 与 `<commit>` | `git show <commit>:<path>`，不混入工作区内容 |
| 分支相对目标分支 | 明确两个引用后使用 `git diff --no-ext-diff --no-textconv <base>...<target> --` | 目标提交内容；旧内容来自合并基点 |

基准/引用不可用、没有共同祖先或合并提交有多个候选父提交时，说明缺口并确认比较对象，不猜 main、不自动 fetch、checkout、stash、reset 或 git add。文件路径正确引用，自动处理文件清单时使用 `-z`，不要按空格拆路径。

- **没有 HEAD**：把当前存在的已跟踪和未忽略新文件作为新增内容读取，可用 `git ls-files --cached --others --exclude-standard -z` 定位后去重；仅暂存模式仍读取索引。不对不存在的 HEAD 执行比较，也不创建提交建立基准。
- **没有可审查差异**：直接说明当前选定范围为空；暂存与工作区相互抵消时说明默认最终状态无净变化，不擅自切成暂存区评审。
- **删除和重命名**：读取旧版本及直接引用方，检查调用、导出和配置是否同步；不把移动文件本身当成缺陷。
- **冲突、二进制、生成文件或超大差异**：说明未解决状态与实际覆盖，优先源文件、接口及配置；不能因少读了文件就声明完整通过。用户只提供补丁或片段时按可用材料评审，关键上下文缺失则指出。

## 2. 追踪必要上下文

先看变更意图和所有文件的改动清单，再阅读改动函数及必要上下文。对具体疑点定向追踪直接调用方、类型/协议、数据模型、配置和相关测试，不默认扫描整个项目。

按受影响组件确认语言/运行时、框架/ORM 与存储及版本，不能由主语言或依赖名称推断全部行为。核对本次实际路径，例如 ORM 求值/加载是否增加访问、异步函数内部是否同步阻塞、数据库改写是否保留过滤和分页语义；不自动加载整套项目健康分析或开发手册。

对于暂存区、历史提交和分支，证据及行号必须属于对应评审版本。当前工作区的修复不能替旧版本证明正确；删除行可标注旧版本位置。评审期间代码变化时，重新核对受影响结论并说明覆盖范围。

## 3. 检查实现合理性、正确性与新增性能问题

先结合需求、调用方契约和已有测试明确这次实现应达到什么目标，再按以下重点评审；目标不明确时指出缺失信息，不自行假设业务规则。

1. **实现是否合理**：方案是否适合当前问题和数据规模，职责、依赖及处理步骤是否清晰，是否增加无必要的复杂度、重复规则或重复工作。建议需说明实际影响及更合适的最小方案。
2. **逻辑是否正确**：结果、状态变化与副作用是否符合需求和契约；核对正常、边界和失败路径，以及权限/数据隔离、兼容性和资源/并发生命周期，不能只看代码能否编译或测试是否存在。
3. **是否引入新的性能问题**：对比改动前后的计算复杂度、内存占用、数据库/网络访问次数、批量规模及阻塞/等待路径，结合实际技术栈和输入规模判断增长，优先发现循环查询、无界读取、关联放大、重复计算和同步阻塞等新增成本。

### 发现的证据要求

每个发现都需要说明：本次哪处改动引入或加重问题，在什么实际条件下触发，影响哪个行为，以及支持判断的代码/契约/测试。必要时读取旧版本确认因果，不把原有问题算成本次发现；原有问题因改动变得可达或加重时可报告。

- 性能问题说明新增的工作量和条件，如循环访问、无界物化、关联放大或同步阻塞；没有运行证据时明确为风险，不虚构生产频次、索引未命中或耗时。
- 设计/可读性问题需有实质依据，如新增循环依赖、职责越界或同一业务规则被重复维护。纯命名偏好、格式和无现实需求的扩展性建议不作为发现。
- 遵循项目约定，避免把其他语言、框架或新版 API 的规则套到当前组件。没有足够证据的疑点放入必要的未验证项，不当作确定缺陷。
- 同一根因合并报告，按影响排序，不设置问题数量配额；正常改动可以没有发现。

## 4. 按需验证

默认静态阅读代码和已有测试。仅在确认具体疑点需要且成本可控时，从项目配置选择少量已有测试、类型或静态检查；不默认完整构建、覆盖率、依赖审计或数据库/浏览器专项。

执行前确认命令及环境符合评审版本。暂存/历史版本与工作区不一致时，不拿工作区测试结果声称已验证该版本；可以完成静态评审并说明缺口。不安装工具、不更新快照、不修改代码或 Git 状态来构造环境；检查只产生正常缓存/临时产物时可以运行。

疑点已被证实或排除后停止无关扩展，不因使用本技能额外启动子代理。缺少依赖或无法运行时如实说明，继续交付已有证据支持的评审。

## 5. 简洁交付

先列发现，按 P0/P1/P2 排序。每条使用 `[P1] 简短标题`，包含准确的文件与最小相关行范围、触发条件、实际影响和最小修复建议。P0 用于无需额外场景假设的严重普遍阻断；P1 为应优先修复的重大问题；P2 为有明确影响的一般问题。

没有发现时说明“未发现可确认的问题”，不等同于全面验证通过。最后简述评审范围、实际执行的检查及重要未验证项；没有执行就标记静态评审，不编造通过结果。

只有用户要求保存时才写评审文档；用户已明确要求修复时，评审后在其授权范围内修改，只请求评审时不修改。本次评审不自动提交、发布或向外部服务发送评论。
