# 数据库性能分析

本文件用于关系型数据库专项。先按 [技术栈](performance-by-stack.md) 确认运行时、框架/ORM 与实际后端，再以“业务入口 → 实际查询 → schema/索引 → 执行计划 → 运行开销 → 验证建议”为链路分析慢查询、索引和高频关联。ORM 源码只是入口，应结合相应加载、求值、缓存与拦截器语义还原查询；下面不是跨栈的统一性能禁令。

## 1. 确定范围与证据

- 从配置、依赖和代码识别数据库、版本、ORM/驱动与连接池，确认主库、只读副本、租户/分区等实际访问位置，不读取或输出真实凭证。
- 读取建表、schema、迁移和 ORM 模型；有授权的实际元数据时对照核对。仓库里的索引声明不证明已经部署，缺少迁移中的索引也不证明线上不存在。
- 优先复用用户提供的慢日志、APM trace、SQL 指纹统计及计划导出，记录环境、采样/统计窗口、重置时间、参数类型和数据规模。只在当前授权范围内补充采集。
- 统计不足不阻塞报告：继续读取源码、列出候选风险及验证资料。不要虚构 QPS、P95/P99、实际索引命中、扫描行数或优化收益。

| evidence_level | 能说明什么 | 不能据此宣称什么 |
| --- | --- | --- |
| `observed` | 已有日志、统计或实际执行记录中的频次、时延、访问路径等，注明具体来源 | 单个实测指标不能证明尚无证据的根因；测试环境不代表生产 |
| `estimated` | 普通 EXPLAIN 给出的访问路径、估算行数和成本 | 已实测慢查、真实扫描行数或具体毫秒耗时 |
| `static_risk` | 查询形状、代码调用关系或声明 schema 暴露的风险 | 运行时确实未用索引、实际调用频次或当前线上故障 |
| `unverified` | 关键条件缺失，保留疑点和所需资料 | 问题已存在、问题不存在或性能已通过验证 |

一项问题可引用多种证据，但各子结论分别写清依据。例如日志证实查询慢，只有源码显示潜在索引风险时，不能直接认定“慢查由索引失效导致”。

## 2. 建立重点查询清单

从用户反馈的接口/任务、实际统计热点及关键读写路径开始。标准模式至少把选中查询追到 SQL 和相关表/索引；深度模式进一步覆盖重要参数分支和已有运行证据。记录具体覆盖范围，不宣称扫描了全部 SQL。

每个查询分配便于引用的 ID，记录：

- 接口/任务及调用链的文件行号、mapper/repository 方法、脱敏 SQL 模板或指纹。
- 表、关联条件、WHERE、ORDER BY、GROUP BY、LIMIT/OFFSET 和返回列；动态 SQL 的重要分支及租户/逻辑删除等隐式条件。
- 仓库声明与实际可用索引的来源、字段顺序、唯一性、表达式/部分索引或分区条件（数据库支持时）。
- 每次业务操作产生的 SQL 数量，包括 ORM 懒加载/预加载、分页 count、序列化时触发的关联、重试和循环调用。
- 可用的运行频次、单次/尾部时延、累计耗时、扫描/返回行数及等待证据；缺失项标记未提供。

不能只搜索 `.sql`。Java 注解和 MyBatis XML、ORM query builder、视图、子查询、动态字符串和数据库函数都可能藏有实际查询。搜索结果回到源码确认，注释和样例不算业务查询。

## 3. 热点与优先级

同时检查“单次慢”和“单次较快但高频”。相同统计窗口内分别查看累计耗时、调用次数、平均/尾部时延及扫描和 I/O 开销，不只看慢日志最慢一条。

- 将语义相同的 SQL 指纹聚合，并回溯到不同调用入口，区分真实调用与重试放大；不能将不同参数分布视为同一条固定计划。
- 用计数差值和明确的采样时长计算窗口频率。单次累计快照、FIRST_SEEN/LAST_SEEN 或总调用次数不足以证明当前 QPS。
- “频次 × 单次耗时/扫描量”只能在同一窗口、相同口径下作为近似开销；累计执行耗时不是 CPU 时间，跨并发调用可以重叠。
- P95/P99 需要已有分布、直方图或原始样本；不能从均值、最大值或计数推算。慢日志有阈值和采样偏差，没记录不代表无热点。
- 区分数据库执行、锁等待、连接池等待、网络传输、对象映射与序列化；有锁/池等待证据时继续追踪事务持锁、连接占用和调用链，不能直接归咎于索引。

优先处理影响关键链路、累计开销大或造成容量问题且有充分证据的查询。静态高风险也可提出高优先级调查，但严重度和证据确信程度分别说明。

## 4. 索引与查询形状

| 排查点 | 具体检查与结论边界 |
| --- | --- |
| 过滤与复合索引 | 对照完整谓词、字段顺序、选择性、等值/范围条件和排序，确认实际用到的前缀及剩余过滤。不要用“范围后面全部失效”等口号代替目标版本计划。 |
| 关联字段 | 两侧字段类型、长度/排序规则、关联条件及索引是否匹配；比较实际访问路径与估算/实测行数，区分唯一关联和一对多。 |
| 表达式与转换 | 列上的函数、计算、类型转换、LIKE 模式、OR 等作为候选风险；核对表达式索引、生成列、优化器重写等支持后再判断。 |
| 扫描与回表 | 命中索引仍可能扫描大量索引项或回表；结合读取/返回行数、过滤、投影宽度和 I/O，不能只看索引名称。 |
| 排序与聚合 | ORDER BY/GROUP BY/DISTINCT 与索引顺序和数据量的关系，是否大量排序、临时结果或落盘；出现排序并不自动等于缺陷。 |
| 分页 | 大 OFFSET 的跳过成本、稳定排序、数据倾斜、列表与 count 的独立代价。游标分页需核对业务跳页需求和排序键语义。 |
| 数据与计划变化 | 统计信息、热点参数、倾斜、实际表大小、分区裁剪和缓存状态；不同参数/环境可能生成不同计划。 |

候选索引建议写明表、字段顺序及其对应的过滤/关联/排序路径，检查是否已有等价或重叠索引，说明写入、存储及维护成本。不要把 `FORCE INDEX`、无限增加覆盖列或建索引当成默认答案。

## 5. 高频多表关联专项

对已观察的高频查询以及源码中的候选关键路径逐项检查：

1. **业务是否需要每张表**：区分返回字段、过滤存在性、权限约束和聚合用途。不能为了性能删除租户过滤、权限判断或有语义作用的 JOIN。
2. **输入与关联基数**：从过滤后的输入开始追踪每个 JOIN 的输出行数，检查漏条件、多对多/多个一对多相乘、非唯一关联及低选择性条件。
3. **重复工作**：内层访问和相关子查询的 loops、同一数据重复查、ORM N+1、分页 count 复用整套复杂 JOIN、先关联大量记录再分页。
4. **行数放大的后果**：重复结果、错误聚合、DISTINCT/GROUP BY 去重、大排序、临时结果/落盘、传输和对象构造成本。
5. **频次放大**：同一窗口的调用数、累计耗时、扫描量和每请求 SQL 数量。没有运行频次时标为“候选高频路径”，不能因函数名是 list 或位于首页就认定高频。

比较满足相同业务语义的候选：更早缩小输入、匹配关联和过滤的索引、仅做存在性判断时的 EXISTS、先聚合再关联、合理的先分页后加载、分批查询、受控冗余/读模型或缓存。每种都说明适用条件；拆 JOIN 可能增加往返、N+1 和一致性问题，先分页可能改变结果，缓存要有失效方案。

不要按“超过三张表”“看到 Nested Loop”“出现全表扫描”直接判故障。小表扫描、低选择性顺序扫描或适当的 hash join 可能合理；大表走索引也可能昂贵。结论取决于实际输入、工作量、频次和目标时延。

## 6. 执行计划与运行统计

只使用与目标数据库版本匹配的字段和解释；不混用 MySQL 与 PostgreSQL 的术语和成本单位。

### MySQL

- 普通计划核对 `type/access_type`、`key`、`key_len/used_key_parts`、`ref`、`rows`、`filtered`、排序/临时结果及关联顺序；`possible_keys` 是候选，`key` 是计划选择，选择索引也不等于有效缩小扫描。
- 普通 EXPLAIN 行数是估算；现成 ANALYZE 导出才包含相应实测指标，注意版本、格式、循环及节点包含关系，不能把父子节点耗时简单相加。
- 已有 Performance Schema 指纹汇总或慢日志用于观察调用次数、累计/均值、扫描与返回行数、临时表等。无索引标志是排查线索，不自动等于性能问题。

仅在已经具备相应授权、工具和统计表时，可适配下列只读汇总查询；否则分析已有导出。该例适用于具备相应字段的 MySQL 8.x，不是自动连接数据库的指令：

```sql
SELECT SCHEMA_NAME, DIGEST, DIGEST_TEXT, COUNT_STAR,
       SUM_TIMER_WAIT / 1000000000000 AS total_seconds,
       AVG_TIMER_WAIT / 1000000000 AS mean_ms,
       SUM_ROWS_EXAMINED, SUM_ROWS_SENT, SUM_CREATED_TMP_DISK_TABLES
FROM performance_schema.events_statements_summary_by_digest
WHERE COUNT_STAR > 0 AND DIGEST IS NOT NULL
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 20;
```

按 `COUNT_STAR` 另看高频排名。Performance Schema 计时以皮秒归一化，上例转换单位；保留原始字段和窗口来源。不要将该结果当成 P99 或当前每秒调用数。

### PostgreSQL

- 普通计划看 scan、Index Cond 与 Filter、连接顺序/算法、估算 rows/width/cost。`cost` 不是毫秒，Seq Scan 不证明遗漏索引。
- 已有实际计划中核对 actual rows、loops、Rows Removed、buffers、sort/hash 内存与落盘及估算偏差。节点 rows/time 通常按循环平均，按 loops 理解工作量，同时避免累加包含子节点的耗时；并行计划按具体节点解释。
- 已启用且有访问权限的 `pg_stat_statements` 可观察 calls、total/mean_exec_time、块读写和临时块；`rows` 是返回/影响行数，不是扫描行数。块命中率也不是“索引命中率”。

具备上述前提时适配下面的只读查询；扩展和字段版本以实际安装为准，不自动安装或开启扩展：

```sql
SELECT dbid, userid, toplevel, queryid, query, calls,
       total_exec_time, mean_exec_time, rows,
       shared_blks_hit, shared_blks_read, temp_blks_written
FROM pg_stat_statements
WHERE calls > 0
ORDER BY total_exec_time DESC
LIMIT 20;
```

按 calls 另看高频排名，时间字段单位为毫秒。记录数据库/用户等统计范围与重置窗口，区分相同 queryid 的不同统计行。其他数据库按实际官方资料适配，不套用本节的 SQL 或阈值。

## 7. 采集边界与验证建议

默认读取仓库和已有证据，不因发现连接串而访问数据库。仅在用户已授权的明确环境中，用现有工具读取必要元数据和普通计划；敏感绑定值脱敏，但保留类型、选择性和边界条件等解释计划所需的信息。

`EXPLAIN ANALYZE` 会实际执行查询；包含写操作、锁、函数或触发器副作用的查询不能因命令叫 EXPLAIN 就运行。健康检查不自动执行 ANALYZE、压测、DDL、刷新统计、配置变更、启用慢日志/扩展或重置统计。实际执行必须已有对应查询和环境授权，普通事务回滚不能消除所有副作用或资源开销。

改进建议包含 SQL/入口、证据、候选方案和验证条件：相同数据库版本、代表性参数与数据规模、统计窗口及可比负载下，对比结果正确性、访问路径、扫描/返回量、时延、累计开销及每请求 SQL 数量。未执行就写待验证，不估造加速倍数；建索引等仅在报告中建议，不在检查时实施。
