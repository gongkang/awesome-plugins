# 项目健康度检查

全自动分析项目完整性，使用并行子代理加速分析，将包含问题清单和修复建议的 Markdown 报告保存到项目的 `docs/` 目录。

本技能用于项目或指定领域的健康评估。用户仅要求 review diff、提交或本次改动时，使用 `code-review` 的轻量评审流程，不启动全项目检查或生成健康报告。

## 分析深度

根据用户请求选择分析深度：

| 深度 | 关键词 | 检测范围 | 性能分析要求 |
|------|--------|----------|----------|
| 快速 | "快速检查"、"quick"、"简要分析" | 默认检查安全、技术债务、文档；用户指定维度时检查对应范围 | 按实际运行时、框架及存储扫描关键路径，不将静态线索当成实测瓶颈 |
| 标准 | 默认、"标准检查"、"完整分析" | 全部 8 个维度，或用户明确指定的维度 | 按技术栈选择运行证据；涉及 SQL 时追踪查询、表和索引，检查慢查及高频关联 |
| 深度 | "深度检查"、"deep"、"详细分析" | 标准内容 + 复杂度分析、重复检测及重点链路深挖 | 比较对应栈的已有运行记录、计划/调用统计和负载条件，评估候选优化与验证方法 |

用户只要求数据库性能、某个接口或其他指定范围时，以该范围为准，不强行启动全部维度；其余维度标记未检查，不用零问题冒充检查通过。分析耗时取决于规模与证据可用性；深度模式不自动获得数据库访问、查询执行或配置变更授权。

## 分析维度

| 维度 | 快速 | 标准 | 深度 | 检测项 |
|------|------|------|------|--------|
| 前后端一致性 | ❌ | ✅ | ✅ | API 契约、数据模型、类型定义 |
| 技术债务 | ✅ | ✅ | ✅ | TODO/FIXME、过时依赖、代码重复 |
| 安全性 | ✅ | ✅ | ✅ | 敏感信息泄露、漏洞模式、依赖漏洞 |
| 性能瓶颈 | 按需 | ✅ | ✅ | 按运行时、框架/ORM 与存储分析；包含慢查询、索引、关联及 API/前端成本 |
| 测试覆盖度 | ❌ | ✅ | ✅ | 测试覆盖率、关键路径覆盖 |
| 代码质量 | ❌ | ✅ | ✅ | 代码风格、复杂度、命名规范 |
| 架构健康度 | ❌ | ✅ | ✅ | 模块耦合、循环依赖 |
| 文档完整性 | ✅ | ✅ | ✅ | README、API 文档、贡献指南 |

## 工作流程

### 阶段 0: 确定分析深度

检查用户请求中是否包含深度关键词，确定分析模式。

**输出进度**:
```
🔍 项目健康度检查
📋 分析深度: 标准
📂 项目目录: /path/to/project
```

### 阶段 1: 项目检测

识别项目类型和技术栈，检测包管理器和框架配置文件。

性能分析需按本次涉及的组件确认运行时及版本、框架/ORM、驱动/存储、同步/异步执行方式和部署形态，并从实际调用路径验证依赖是否被使用。多包或多进程项目分别识别；语言相同不代表执行模型、ORM 行为或数据库相同，详细分流见 [按技术栈分析性能](references/performance-by-stack.md)。

**输出进度**:
```
📦 项目类型检测中...
  ✓ Node.js 项目 (package.json)
  ✓ TypeScript (tsconfig.json)
  ✓ React 前端
```

### 阶段 2: 并行分维度分析

**重要**: 使用子代理并行分析各维度，以提高效率。

根据分析深度和用户指定范围，启动相关维度的子代理；下列是完整检查的任务划分，按可用并发额度分批调度。只分析性能时仅执行性能任务。

**快速模式 (3 个并行代理)**:
- 代理 1: 安全性分析
- 代理 2: 技术债务分析
- 代理 3: 文档完整性分析

**标准/深度模式 (8 个并行代理)**:
- 代理 1: 前后端一致性分析
- 代理 2: 技术债务分析
- 代理 3: 安全性分析
- 代理 4: 性能瓶颈分析
- 代理 5: 测试覆盖度分析
- 代理 6: 代码质量分析
- 代理 7: 架构健康度分析
- 代理 8: 文档完整性分析

**输出进度**:
```
🔄 启动并行分析代理...
  ✓ 代理 1/8: 前后端一致性 - 运行中
  ✓ 代理 2/8: 技术债务 - 运行中
  ...
```

## 子代理分析任务定义

以下是每个子代理的具体分析任务：

### 代理 1: 前后端一致性分析

**任务**: 分析项目的前后端一致性

**分析步骤**:
1. 查找 API 定义文件（OpenAPI/Swagger、GraphQL Schema、tRPC）
2. 查找前端 API 调用代码
3. 查找数据模型定义（Prisma、TypeORM、Django Model）
4. 对比检查一致性

**返回格式** (JSON):
```json
{
  "dimension": "前后端一致性",
  "issues": [
    {"severity": "high|medium|low", "location": "file:line", "description": "...", "suggestion": "..."}
  ],
  "summary": {"total": 0, "high": 0, "medium": 0, "low": 0}
}
```

### 代理 2: 技术债务分析

**任务**: 分析项目的技术债务

**分析步骤**:
1. 统计 TODO/FIXME/HACK 注释
2. 检查过时依赖（npm outdated / pip list --outdated）
3. 检测代码重复（深度模式）

**返回格式**: 同上，dimension 为 "技术债务"

### 代理 3: 安全性分析

**任务**: 分析项目的安全性

**分析步骤**:
1. 检测硬编码密钥和敏感信息
2. 检查常见漏洞模式（XSS、SQL注入、命令注入）
3. 运行依赖漏洞扫描（npm audit / pip-audit）

**返回格式**: 同上，dimension 为 "安全性"

### 代理 4: 性能瓶颈分析

**任务**: 根据实际技术栈分析业务路径的性能瓶颈；涉及数据库时重点识别慢查询、索引访问问题和高频多表关联。

先读 [按技术栈分析性能](references/performance-by-stack.md) 的选择方法及相关条目，组合运行时、框架/ORM 和存储的分析方式。发现关系型数据库访问或用户明确关注 SQL 时，再读 [数据库性能分析](references/database-performance.md)。MongoDB、Redis、浏览器等使用各自证据，不能套 MySQL 字段；源码搜索只定位候选。确认没有数据库访问时将数据库部分标为不适用；找不到连接配置本身不能证明没有数据库访问。

**分析步骤**:
1. **识别环境与证据**：先确定组件的运行时、框架/ORM、执行模型和存储版本，再选择已有 trace、profile、GC/线程/事件循环/连接池指标、浏览器记录或数据库证据。关系型存储核对 schema、迁移及实际索引；区分仓库声明与部署状态。
2. **追踪实际工作**：沿请求/任务追踪等待、计算、分配及 I/O。涉及 SQL 时建立接口 → service/repository/mapper → 实际 SQL → 表与索引清单，结合 ORM 求值/加载/缓存和拦截器展开动态分支、隐式关联及分页 count，不能只按 ORM API 名称判断。
3. **定位热点**：结合相同窗口内的频次、累计耗时、单次时延和相应运行时/存储证据排序；SQL 访问还核对扫描/返回行数与 I/O/等待。单次不慢的高频操作也要检查；没有运行指标时只标记候选热点。
4. **SQL 索引与计划**：仅对相关关系型访问，对照 WHERE/JOIN/ORDER BY/GROUP BY 与索引字段、顺序、类型和实际访问路径，检查扫描放大、过滤、排序和回表；不能凭存在索引或 possible_keys 就认定命中有效。
5. **SQL 高频多表关联**：检查关联条件、驱动输入、每侧行数、循环次数、一对多行数放大、DISTINCT/GROUP BY 补救、排序/临时结果和重复 count 成本。关联表数是线索，不直接作为故障结论。
6. **对应存储访问成本**：按框架与后端检查隐式额外访问、无界读取、重复查询、批量规模、物化/序列化和等待；SQL 还关注大 OFFSET、相关子查询及事务持锁。区分数据操作本身慢与池/锁、网络或对象处理慢。
7. **分析对应运行时与前端**：按栈区分 CPU、GC/分配、线程/锁、事件循环或协程阻塞与 I/O 等待；前端区分网络、脚本、渲染/布局及 SSR/水合。只采用当前组件适用的证据，不以构建目录大小、lazy 数量或异步关键字定性。
8. **提出可验证的建议**：说明适用组件、版本和方法；数据库建议关联具体 SQL 与访问路径，运行时/前端建议关联相应热点和记录。给出语义、资源及维护取舍和同条件验证方式，不执行修复。

**返回格式**: 保留公共返回格式，dimension 为 "性能瓶颈"。性能 issue 附加 `component`（实际运行时/框架/存储及版本）、`entrypoint`、`evidence_level`、`evidence` 和 `verification`；SQL 问题另附 `query_id`，其他问题不编造 SQL。数据库示例：

```json
{
  "severity": "medium",
  "location": "<实际 SQL 或 mapper 的文件:行号>",
  "description": "查询存在扫描放大风险，当前缺少运行计划，尚未确认实际慢查",
  "suggestion": "<结合查询和索引给出候选改进>",
  "component": "<实际运行时、框架/ORM 与存储及版本>",
  "query_id": "Q1",
  "entrypoint": "<实际接口/任务及调用位置，无法确认则注明>",
  "evidence_level": "static_risk",
  "evidence": ["<源码、schema、计划或统计的实际证据及来源>"],
  "verification": "<所需计划/统计或隔离环境中的对比方法，未执行则注明>"
}
```

证据等级为 `observed`（运行证据）、`estimated`（估算计划）、`static_risk`（源码/配置风险）、`unverified`（不足以判断）。每个结论的强度与对应证据一致，不能用实测时延替另一个未验证的索引或运行时原因背书。另附实际审查的组件/查询、采用的方法、参数/环境范围和缺失证据；去重后再汇总，不能将同一根因的多处调用重复计为独立缺陷。

### 代理 5: 测试覆盖度分析

**任务**: 分析项目的测试覆盖度

**分析步骤**:
1. 查找测试文件
2. 运行测试覆盖率报告（如可用）
3. 识别未覆盖的关键文件

**返回格式**: 同上，dimension 为 "测试覆盖度"

### 代理 6: 代码质量分析

**任务**: 分析项目的代码质量

**分析步骤**:
1. 检查 linter 配置和警告
2. 检测代码复杂度（深度模式）
3. 检查命名规范

**返回格式**: 同上，dimension 为 "代码质量"

### 代理 7: 架构健康度分析

**任务**: 分析项目的架构健康度

**分析步骤**:
1. 检测模块耦合度
2. 检测循环依赖
3. 检查依赖方向

**返回格式**: 同上，dimension 为 "架构健康度"

### 代理 8: 文档完整性分析

**任务**: 分析项目的文档完整性

**分析步骤**:
1. 检查 README 文件
2. 检查 API 文档
3. 检查 CONTRIBUTING 和 CHANGELOG

**返回格式**: 同上，dimension 为 "文档完整性"

## 阶段 3: 汇总报告

收集所有子代理的分析结果后，执行以下步骤：

1. **合并问题清单**: 将所有代理返回的 issues 数组合并
2. **统计摘要**: 计算各维度的问题数量和严重程度分布
3. **排序优先级**: 按严重程度排序问题
   - 性能问题同时考虑累计开销、频次、关键路径影响及证据等级；不能只按最慢单次查询或关联表数量排序。频次和时延来自同一口径，缺失指标写明未提供。
4. **生成修复建议**: 针对发现的问题说明涉及的位置、建议改动和验证方式，按优先级写入报告
5. **保存报告**: 使用下面的模板生成 Markdown 报告，按「报告保存位置」保存到项目的 `docs/` 目录

将报告直接保存到被分析项目的 `docs/` 目录下；目录不存在时创建：

- 每次生成报告都使用带时间戳的路径: `docs/project-health-report-YYYYMMDD-HHMMSS.md`
- 将 `YYYYMMDD-HHMMSS` 替换为本次报告生成时间，并在交付时返回实际保存路径
- 问题清单与修复建议保存在同一份报告中，不在项目根目录或额外子目录生成文档

## 注意事项

1. **并行优先**: 使用 Agent 工具同时启动多个子代理分析各维度
2. **自动检测**: 尽量使用自动化工具检测，减少主观判断
3. **问题分级**: 使用 🔴 高 / 🟡 中 / 🟢 低 三级严重程度
4. **可操作建议**: 每个问题都要给出具体的修复建议
5. **只读分析**: 除写入 `docs/` 下的健康度报告外，不修改项目代码，不执行修复或提交
6. **数据库执行边界**: 默认分析源码和已有导出；只在已授权的明确环境采集相应只读元数据或普通执行计划。`EXPLAIN ANALYZE` 会执行查询，不能当作普通只读检查自动运行；不自动建索引、刷新统计、启用日志/扩展、重置计数或做压测。缺少授权或证据时交付已完成的分析和待验证项。
