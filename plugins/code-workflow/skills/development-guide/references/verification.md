# 验证方式

用于本次改动的验证和交付，不要求创建新的项目检查体系。

## 找到实际命令

先检查当前包的项目指令、清单、任务脚本、构建配置和 CI。记录实际工作目录、运行时版本、命令及所需服务。不要从语言名猜命令，也不要在未读取脚本前运行可能发布、迁移或修改外部数据的任务。

| 技术栈 | 优先查找的位置 |
| --- | --- |
| TS/JS | 包级 `package.json` scripts、锁文件、TS 配置、工作区配置及 CI |
| Python | `pyproject.toml`、tox/nox、Makefile、依赖与环境配置及 CI |
| Java | Maven/Gradle wrapper、POM/构建脚本中的插件与 profile、模块关系及 CI |
| Go | `go.mod`、`go.work`、任务脚本、构建标签及 CI |

复用已有格式、lint、类型、测试及架构规则。确认支持时使用检查模式，避免无关格式化。缺少工具时说明缺口和建议；不自动安装工具、修改 CI 或添加整套规则。

## 根据变化选择证据

| 改动 | 优先验证 | 不能代替的检查 |
| --- | --- | --- |
| 纯规则或算法 | 有意义的输入输出、失败与边界用例 | 格式通过不能证明规则正确 |
| 数据访问与事务 | 实际数据库语义、映射、唯一约束和回滚场景 | 全 mock 测试不能证明事务生效 |
| API 或公开库契约 | 调用方兼容性、序列化、错误映射与相关集成测试 | 类型通过不能证明外部输入合法 |
| UI 和状态 | 用户行为、状态转换、加载/空/错误路径 | 组件快照不能单独证明交互正确 |
| 并发与任务 | 重复、取消、退出、清理和必要的竞争检测 | 单次成功不能证明并发安全 |
| 模块重构 | 既有行为、公开契约、实际依赖与相关架构检查 | 移动文件不能证明耦合降低 |

对行为变更和已修缺陷补充能发现回归的测试；避免为低影响文档改动、纯转发函数或实现细节机械加测试。不要为了满足测试注入生产环境后门或跳过关键规则。

运行足以覆盖当前变化的检查。通过后，除非新改动、失败或未决问题需要，不反复扩大检查。长耗时检查可以先运行相关测试，再执行项目要求的完整检查。

## 设计自查

- 从公开入口能否解释正常和失败路径，名称和注释能否说明业务语义？
- 规则、状态、事务与资源是否各有明确归属？跨模块是否仅访问公开契约？
- 新抽象解决了什么真实问题？同一行为是否因无用途的分层变得更难追踪？
- 对本次涉及的持久化、并发或网络行为，是否验证了相关故障场景？
- 公开契约、配置或数据变化是否影响现有使用方？

没有依赖分析工具时，读取实际 import、构造参数、注册和调用链进行检查，不声称已完成自动化架构扫描。已有 P3C、PMD 或其他工具通过，也不能据此宣称满足所有设计和业务要求。

## 如实交付

说明改动结果、必要的取舍和实际验证。验证结果包含已执行的命令及结果；失败时区分本次新增问题、已知基线和环境阻碍，并说明依据。没有执行就标记未运行及原因。

对尚未检查的兼容性或关键失败路径明确说明。不要以覆盖率数字或“全部符合指南”代替实际证据，也不要生成本次任务没有要求的审计报告。
