# Go

目录依据交付用途及 Go 官方指导选择，其他设计条目是本指南的工程建议。先确认 `go.mod`、构建标签、工作区与 CI 版本。

## 目录与包

| 用途 | 默认布局 |
| --- | --- |
| 小型库 | 模块根目录的包和同目录测试，必要时增加有明确职责的子包 |
| 小命令 | 根目录 `main` 包及测试，复杂度增长后再拆内部包 |
| 服务或多个命令 | `cmd/<app>/main.go` 负责组装；`internal/<业务能力>/` 承载不对外公开的实现 |

`cmd` 不是所有命令项目的必需目录；`pkg` 也不是公开包的强制目录。不要把库都放进 `internal` 导致外部无法使用。一个目录一个包，测试包的语言约定例外；包名和导出围绕具体能力，避免 `util`、`common` 成为杂物集合。

业务包内可包含处理、数据访问和规则，不机械复制 Controller/Service/DAO 三套包。跨包使用导出契约，保持无循环依赖。

## 接口与状态

- 优先在消费者真正需要替换或隔离依赖的位置定义小接口；不要为单一实现批量生成接口，也不要让实现包预设所有消费者需求。
- 具体类型通过构造函数或参数传入实际依赖。简单纯函数直接调用，避免为每次调用创建工厂和注册表。
- 接收者、指针和值语义保持一致并说明状态归属。不可复制的同步对象、共享映射和切片引用需要关注实际并发访问。
- 对外导出保持最小，文档说明关键契约、阻塞、线程安全和资源所有权；返回的内部可变数据不能无意间成为外部修改入口。

## 错误、I/O 与并发

- 检查返回的错误，增加操作上下文时保留需要识别的原因，例如使用适合目标版本的 `%w`；调用方按约定使用 `errors.Is/As`，不要匹配错误字符串。
- 可预期的业务失败通过返回值/错误表达，不以 panic 作为普通流程；不要既记录错误又逐层重复记录同一堆栈。
- 请求上下文按调用链传递，通常作为首个参数；不要为绕开取消随意换成 `context.Background()`，不要把业务可选参数塞进 context。
- 远程调用设置适当超时；获取资源成功后安排关闭，核对 `defer` 的作用域，避免循环中延迟释放大量资源。
- 启动 goroutine 前说明由谁取消、等待和接收错误；明确 channel 的关闭方、并发上限及退出条件，避免无人等待的后台任务。
- 并发修改共享数据需选择合适的同步和所有权方式。请求取消、子任务失败及部分结果返回都应有清楚语义。

```go
// 反例：忽略底层错误后返回看似成功的零值。
item, _ := repository.Load(ctx, id)

// 改进片段：Load 的调用方可以区分失败并获得操作上下文。
item, err := repository.Load(ctx, id)
if err != nil {
    return Item{}, fmt.Errorf("load item %s: %w", id, err)
}
```

示例中的类型、错误约定和导入需适配项目；不要无条件把“未找到”转换成系统错误。

## 验证与来源

复用项目现有 `gofmt` 检查、`go vet`、测试及 lint 配置，不自动引入工具集合。测试可按行为组织表驱动用例，错误路径要有实际断言；涉及共享状态时，环境支持且项目适用时运行 race 检查。构建标签、CGO 和集成服务要求先从项目确认。

- [Organizing a Go module](https://go.dev/doc/modules/layout)：库、命令和服务的布局选择及 `internal` 边界。
- [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments)：命名、错误、接口、context 与 goroutine 生命周期等评审建议；该文档自身并非完整风格手册。
