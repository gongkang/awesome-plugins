# 设计与可读性

本文件是跨语言的工程建议，不是某个语言或企业手册的逐条转录。用于确定模块、职责、依赖和代码表达；具体语法与工具遵循项目及语言参考。

## 结构从用途和变化点开始

先回答：项目交付什么，哪些规则一起变化，状态由谁维护，哪些能力需要对外稳定。目录用于表达这些答案。

| 项目用途 | 默认组织方式 | 何时继续拆分 |
| --- | --- | --- |
| 一次性脚本或小 CLI | 入口加少量职责明确的函数；需要时拆包 | 出现可独立说明的业务能力或资源边界 |
| 库或 SDK | 围绕使用者概念组织公开 API，隐藏实现 | API 有独立归属、发布或依赖需求 |
| 前端应用 | 框架路由/启动入口、业务功能、稳定共享能力 | 功能拥有独立状态、交互或复用边界 |
| 后端服务 | 薄入口、业务模块、实际外部依赖的适配 | 模块规则或实现确有不同变化原因 |
| 多包仓库 | 保留现有应用/包边界及各自配置 | 独立消费、发布或依赖约束有实际需求 |

不要以“企业级”为理由生成每层一个目录、每类一个接口、多套相同数据模型或独立服务。先在一个进程内明确模块边界；服务拆分需要真实的部署、隔离或组织需求。

## 高内聚：明确业务和状态归属

- 以业务能力聚合共同变化的实现和测试。例如订单的状态规则、定价及状态变更编排属于订单能力；持久化细节可在其内部隔离。
- 入口承担协议解析和响应映射，业务规则放在可以直接调用、验证的函数或对象中。简单 CRUD 可以使用较少层次。
- 为每种状态和业务规则指定一个维护位置。其他模块通过公开能力操作它，避免多处直接修改同一业务表或内存状态。
- 公共目录只接收有明确共同语义和稳定消费者的能力；名称相近或代码相似不足以证明应共享。业务规则不同的重复代码可以暂时分开。
- 只有确有边界差异时才拆分请求、业务、持久化模型，例如信任、生命周期或字段暴露不同；避免为相同数据机械增加转换链。

## 低耦合：依赖可追踪

描述本次涉及模块的职责、公开契约、允许的依赖和内部实现。一个模块不应依赖另一个模块的私有路径、表结构或隐藏状态。

```text
入口 → 用例/业务能力 → 实际需要的依赖契约
                             ↑
                    数据库/远程服务适配实现
启动或组装位置连接业务能力与具体实现
```

此图是有外部依赖时的组织示例。简单业务可直接调用具体类或函数；协议解析、SQL、网络调用等细节不应反向决定可独立表达的核心规则。

发现循环依赖时，先检查职责归属：是双方共享了一个应有独立归属的规则，还是某一方访问了不该知道的内部实现。只把一方代码挪进 `common` 并不能证明循环已合理解决。

| 反例 | 更合适的改进 | 验证依据 |
| --- | --- | --- |
| 订单直接调用支付模块的内部 SQL 文件 | 调用支付公开能力，由支付维护自己的数据 | 修改支付存储实现时，订单契约测试不变 |
| `GlobalContext` 提供数据库、时间和用户状态 | 显式传递本次行为需要的值或协作者 | 从签名能看出依赖，测试能独立构造 |
| 为单一纯计算函数创建通用工厂和注册中心 | 直接函数调用，实际有可替换行为时再引入策略 | 调用链更短，保留相同行为验证 |
| `utils` 中混合折扣规则、HTTP 请求和格式化 | 规则回到对应业务；I/O 在边界；纯格式化按消费者归属 | 业务变更无需修改无关共享模块 |

依赖注入可以是构造器、函数参数或语言自然支持的组合，不要求引入容器。引入接口时能说明消费者、替换需求或需要隔离的外部依赖。

## 可读性：让控制流和语义显式

- 函数名表达行为，变量名表达业务含义与单位。对金额、时长、时区、标识符和可空值明确约定，避免含义模糊的布尔参数。
- 一个函数维持同一抽象层级：编排函数调用命名明确的业务步骤，具体规则在相应步骤内表达。不要把每行代码包装成仅转发的函数。
- 用提前返回减少无关嵌套；把复杂条件命名为业务判断；为必须保留的处理顺序、锁或事务边界写清原因。
- 返回值、异常和状态明确表达成功、缺失及失败。不要将错误转换为看似成功的空对象或默认值；缺失本来属于正常结果时除外。
- 注释说明契约、原因、限制和非显然算法；同步更新相关注释。遵守语言要求的公共 API 文档，不用重复代码含义的注释增加噪声。
- 按职责和变化原因判断是否拆分。行数、嵌套和参数数量是检查信号；只有项目或适用来源明确规定时才作为门槛。

下面仅展示控制流表达，重构时必须保持原本的分支顺序和错误语义：

```ts
// 反例：正常路径隐藏在嵌套内。
function canSubmit(order: Order): boolean {
  if (order.status === "draft") {
    if (order.items.length > 0) {
      return true;
    }
  }
  return false;
}

// 改进：业务条件直接可读。
function canSubmit(order: Order): boolean {
  return order.status === "draft" && order.items.length > 0;
}
```

## 按本次行为检查数据和故障

| 涉及的行为 | 需要明确的问题 |
| --- | --- |
| 修改持久化数据 | 不变量在哪里维护，事务覆盖哪些操作，失败如何回滚，迁移和旧数据是否兼容 |
| 并发修改或重复请求 | 如何避免更新丢失，幂等键和唯一约束由谁维护，锁或任务如何退出 |
| 远程请求、消息或后台任务 | 超时、取消、有限重试及错误传播；重复副作用、消息重复和失败补偿怎样处理 |
| 缓存 | 数据归属、失效时机、一致性要求；缓存失败是否允许降级 |
| 不可信输入和资源访问 | 在边界做运行时校验及身份、资源归属检查；避免注入和意外字段暴露 |
| 配置、凭证与日志 | 配置来源和启动校验；凭证使用现有安全配置渠道；日志有上下文但不泄露敏感信息 |

不要在所有任务中添加重试、缓存、锁、事件总线或降级。选择最小的、能满足当前行为要求的机制，并验证失败路径。性能优化依据实际查询、访问规模或测量，不凭空修改结构。
