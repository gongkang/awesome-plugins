# 制定或更新项目开发指南

仅在用户要求制定、保存或更新项目指南时使用。只要求建议时在对话中回答，普通编码不额外生成文档。

## 选择位置与事实

1. 搜索已有开发指南、贡献约定、架构决策和项目指令中的文档引用，确认哪份文件承载本次内容。优先原位更新，保留有效约定及人工内容。
2. 用户指定位置时按其要求；没有既有承载文档时默认 `docs/development-guide.md`。目录不存在则创建，不另建多个相互重复的规范文件。
3. 根据实际配置和代表性代码写指南。标明已经采用的约定、计划采用的建议及尚未查明的事实；不把建议目录描述为当前事实。
4. 采用共同原则及当前语言、框架参考。手册等外部来源记录版本、条款和等级；列出实际适用的冲突或例外及处理理由。
5. 不自动改写 `AGENTS.md`、`CLAUDE.md` 或其他项目指令文件。只有用户要求相应集成时，才在正确作用域补充引用，避免复制整份指南。

## 文档应回答的问题

按项目规模合并相关内容，不强制创建空章节。下表是内容要求，不是固定篇幅模板。

| 内容 | 要写出的项目事实或决策 |
| --- | --- |
| 技术基线与来源 | 语言/运行时和框架版本、应用或包范围、规范来源及核对日期 |
| 项目结构 | 当前或建议目录树、各目录职责；框架保留目录与小项目的简化方式 |
| 模块和依赖 | 实际业务模块的归属、公开入口、允许的依赖；内部实现的边界和启动组装位置 |
| 编码与可读性 | 本项目命名、类型/空值、错误、副作用和注释约定；对关键反例给出简短改进 |
| 数据与集成 | 本项目实际存在的事务、数据模型、SQL、远程请求、并发和幂等要求 |
| 安全与运维 | 与当前用途有关的校验、权限、配置、凭证、日志和故障定位方式 |
| 测试与检查 | 从配置确认的命令、工作目录、依赖条件及检查范围；缺少的能力明确标记 |
| 兼容与例外 | 旧结构如何渐进采用；外部参考与项目约定差异及理由 |

对关键规则使用“适用场景 → 项目做法 → 验证证据”的表达。例如：涉及库存扣减时，由库存模块维护原子更新和失败语义，通过现有并发或集成测试验证。不要仅写“遵循高内聚低耦合”。

对新项目给出本次推荐结构及理由；对旧项目只说明相关改进路径，写指南不等于获得执行架构迁移、改数据库或建设 CI 的授权。

## 完成交付

检查文件引用、目录名称和命令是否符合项目；清除空表格和未完成占位符；确认来源等级和补充建议没有混淆。向用户返回实际保存路径和主要采用决策，并说明未验证的命令或待确认事项。
