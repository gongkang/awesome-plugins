# 可读性细则

用于新建或实质改写的手写业务代码。目标是让接手的人容易理解目的、规则和处理步骤；不能只满足编译、测试或行数。项目约定和 formatter 优先；没有约定时使用本文件的默认指导。

## 文件与函数大小

以下数字是本指南为 AI 辅助开发选择的建议值，不是语言官方标准或统一硬门槛。按格式化后的物理行理解：文件计全文件，函数从签名到结束，包含空行和注释；语言/项目来源另有计数口径时单独说明。

| 对象 | 默认目标 | 超出后如何处理 |
| --- | --- | --- |
| 手写业务文件 | 尽量不超过 300 行 | 超过 500 行时，检查是否混合多个职责，优先沿独立业务能力、状态归属或外部依赖边界拆分；保留时说明具体原因。 |
| 普通业务函数/方法 | 尽量不超过 40 行，短于此值无需补足 | 超过 50 行时检查抽象层级、阶段和分支；超过 80 行优先提取可命名、可验证的业务步骤，确需保持连贯时说明理由。 |
| 嵌套控制流 | 尽量不超过 3 层 | 检查提前返回、命名业务判断或提取步骤的机会；不要为减少一层缩进打散紧密相关的状态或事务。 |

- 低于建议值仍可能职责混杂；超过建议值也不自动等于错误。检查实际阅读成本、共同变化原因、参数/状态传递和调用链长度。
- 不为压行删注释、删空行、合并多条语句或调宽 formatter 列宽。不把一个长函数切成若干 `step1/step2` 或只转发的函数。
- 提取后的函数应有明确业务名称、输入输出和归属。小型且内聚的辅助函数可留在同文件；只有形成独立职责或边界才移动到其他文件。
- 纯声明、DTO、schema、常量/测试数据、生成代码和连续算法按实际形态判断；不手改生成文件，也不将所有 JSX/模板一概豁免。混合数据请求、状态、副作用和多个界面的巨型组件仍需按职责整理。
- 旧大文件的局部修复只改善本次涉及的逻辑和注释，不自动重构整个模块。保留例外的理由在必要的交付说明中简述，不强制创建新报告或给每个文件写行数注释。

## 哪些代码需要注释

公共入口/跨模块 API 及非平凡业务函数应有函数级说明，即使名称清楚，也需交代不显然的规则与契约。项目未规定注释语言时，采用用户沟通语言；标识符和专有术语保持准确。

| 情形 | 应说明的内容与位置 |
| --- | --- |
| 公共 API、导出函数、接口方法、重要类/模块 | 在语言约定的位置说明用途；补充无法从类型和命名得知的输入单位、空值/返回语义、错误、副作用或调用限制。 |
| 承载业务判断、状态转换或多步编排的函数 | 函数级说明写出业务目的及关键规则；内部按实际阶段添加简短说明，使处理顺序可追踪。 |
| 公式、舍入、排序、去重、优先级和兜底 | 在规则实现前写清依据、边界或特殊选择，尤其是同分规则、金额/时间单位和业务例外。 |
| 锁、事务、取消、清理、幂等或重试 | 在关键位置解释顺序、保护的不变量和失败处理依据，避免维护者随意交换步骤。 |
| 批量、缓存、索引相关写法或性能优化 | 说明实际要减少的工作、适用条件与一致性/内存等取舍；不能编造测量结果和性能倍数。 |
| 兼容旧协议、第三方缺陷或临时绕行 | 解释为何存在及何时可移除，有已有 issue/协议来源时引用；不写没有依据的历史背景。 |
| 简单 getter/setter、直观转换或薄转发 | 可省略重复语句含义的解释性注释；项目或语言要求的文档注释仍照常提供。 |

函数级说明先用一句话讲清“做什么、服务于什么规则”，再按实际需要补充契约。不要机械复制完整签名、重复已知类型，或生成每个字段都为空的 `@param/@return` 模板。短函数的一行说明可以足够，复杂函数应补充必要细节。

内部块注释应表达阶段目的或关键原因，如“只在全部校验通过后写入，避免部分成功”；避免“获取数据”“执行处理”等没有业务信息的标题。不要逐行翻译赋值、循环和 return，也不要给每个 if 都加注释。

注释必须与实际实现和已知需求一致。无法确认规则来源时查代码、测试或约定，仍不清楚则说明待确认；不为凑解释而捏造业务动机。修改行为时同步更新注释，删除失效、误导或长期注释掉的废代码。

## 空行、换行与视觉结构

- 在导入、常量/类型、主要声明等不同职责之间保留语言约定的间隔，相关声明按用途聚合。
- 函数内部在实际语义边界使用一个空行，例如校验与归一化结束、准备数据结束、进入核心计算或执行副作用前；同一紧密逻辑块不逐行留空，也不机械每隔几行插空行。
- 长条件先检查是否能命名为业务判断；长参数、链式调用、集合/对象字面量按语法边界和现有 formatter 分行，避免嵌套三元表达式和密集单行控制流。
- 一行保持一个独立动作；不要用分号、逗号表达式或过度紧凑的推导式挤入多个步骤。简单、符合语言习惯的表达式可以保留。
- 块注释紧贴它解释的逻辑块，分隔空行放在块之前；声明级注释和声明之间不随意插入空行。decorator/annotation 与目标声明的关联应保持。
- 先遵守语言和项目的 formatter，再人工检查业务分组。不要因为 formatter 通过就省略语义空行，也不与 formatter 反复拉扯无关布局。

## 语言适配

| 语言 | 采用方式 |
| --- | --- |
| TS/JS | 公共入口和非平凡函数按项目惯例使用 JSDoc/TSDoc，复杂实现内用块/行注释。文档说明业务语义，避免用重复类型标签淹没 TypeScript 签名；保留现有 Prettier/ESLint 等格式约定。 |
| Python | 公共函数、类/模块及非平凡业务函数使用 docstring；多行 docstring 的概要和细节之间留空行。无相反项目约定时，顶层函数/类之间留两个空行，类方法之间一个；函数内按逻辑留空行。 |
| Java | 遵循项目及阿里巴巴手册的 Javadoc 要求，简单 getter/setter 的解释性注释例外不取消其文档要求。手册的方法 80 行规则是推荐且不含注释，单行 120 字符是原强制条款；它们与本文件自定建议分开解释，不静默改变来源等级。 |
| Go | 导出声明提供以名称开头的 doc comment，紧贴声明且中间不留空行；按实际契约说明并发、阻塞及资源归属。用 gofmt 保持格式，保留有语义的逻辑分组，不套 Java 缩进或 Python 声明间隔。 |

## 简短示例

以下自拟示例的约定是：输入和输出以分为单位，允许折扣超过原价，但保留最低应付额；任何负数输入均报错。示例仅展示契约注释和逻辑分组，不是要求所有项目采用这项业务规则。

```python
# 改进前：缺少契约和业务例外说明，校验与计算挤在一起。
def payable(subtotal_cents, discount_cents, minimum_cents):
    if subtotal_cents < 0 or discount_cents < 0 or minimum_cents < 0: raise ValueError("negative amount")
    return max(minimum_cents, subtotal_cents - discount_cents)
```

```python
def payable(subtotal_cents: int, discount_cents: int, minimum_cents: int) -> int:
    """计算折后应付金额，所有输入和返回值均以分为单位。

    任一输入为负数时抛出 ValueError，不产生外部副作用。
    """
    if subtotal_cents < 0 or discount_cents < 0 or minimum_cents < 0:
        raise ValueError("negative amount")

    # 折扣允许超过原价，仍按示例业务约定保留最低应付额。
    discounted_cents = subtotal_cents - discount_cents
    return max(minimum_cents, discounted_cents)
```

注释和空行使示例更长，但契约和规则更容易理解；不能为了行数目标退回密集的一行写法。
