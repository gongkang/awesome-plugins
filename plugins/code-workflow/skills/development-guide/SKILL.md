# 开发指南

让本次改动容易理解、职责清楚、依赖明确，并通过项目现有方式验证。先发现约定，再选择指南，最后验证改动；新项目给出明确默认值，旧项目在任务范围内渐进改善。

## 选择工作方式

- **开发或重构**：直接把相关指导应用于已授权的改动；不因为使用本技能而自动生成指南文档、审计报告或迁移整个项目。
- **制定或更新指南**：基于项目事实编写可执行的开发指南，先读 [指南交付](references/project-guide.md)。用户只要求建议或讨论时直接在对话中回答。
- **指南符合性评审**：用户明确要求按开发指南或项目规范评审时，检查相关约定的适用性与符合情况。日常 review diff 或检查本次改动使用 `code-review`，不因评审自动生成指南或全项目报告。

## 先发现项目约定

使用有针对性的文件搜索和读取，确定：

1. 用户指定范围，以及适用的项目指令、开发指南、架构决策和贡献约定。
2. 本次涉及的包、语言及运行时版本、框架、入口、构建与包管理方式。多包仓库分别识别，不把根目录配置套到每个包。
3. 一条代表性的业务路径及对应测试：谁接收输入，谁拥有规则和状态，谁访问外部系统，谁组装依赖。
4. 已配置的格式检查、静态检查、测试和 CI 命令，以及它们的工作目录和前置条件。

从配置和代码确认事实，不凭文件夹名称推断架构。上下文不足时继续探索；只有会影响行为、契约或架构选择且无法查明的信息才向用户澄清。

## 应用指导

- 用户要求和项目既有约定优先；缺少约定时采用相应语言的默认结构。明确区分项目事实、来源条款和本指南的建议。
- 外部条款保留原始等级和适用条件。“推荐”不能写成强制要求；不能把框架补充建议归为阿里巴巴原文。来源中的数字限制保留其条件，不扩散为跨语言门槛。
- 外部条款与项目约定冲突时，说明条款、差异及本次采用的方式。涉及正确性或安全问题时指出实际影响并修复授权范围内的问题，不以沿用旧代码为理由忽略缺陷。
- 新项目采用满足当前用途的最小结构。保留框架规定的路由、包和生命周期；不预建空分层，不默认引入微服务、DDD、CQRS 或多构建模块。
- 既有项目沿用合理的模块和命名，在相关位置改善。跨模块重构、公开契约变更和数据迁移必须属于当前任务范围；发现更大问题时给出具体建议。
- 按业务能力聚合共同变化的规则、状态和测试；跨模块通过公开契约协作。在实际外部依赖或变化边界引入抽象，避免凭空添加接口、基类和工厂。
- 代码表达输入、输出、错误、状态变化和副作用。优先业务命名、平直控制流及一致抽象层级，注释补充原因、约束和契约。
- 涉及持久化、并发、远程调用、权限或敏感数据时，核对相关的数据一致性、故障处理和安全指导；纯局部改动不附加无关流程。

## 验证与交付

使用现有工具验证能够机械检查的部分，设计自查负责可读性和职责边界。具体方法见 [验证方式](references/verification.md)。

交付前确认：

- 业务行为、失败分支及需要兼容的契约有对应验证；本次改动没有新增循环依赖或跨模块内部访问。
- 没有以“更通用”为由引入缺少实际用途的抽象，没有把业务逻辑堆入公共工具、入口或视图。
- 运行相关的现有检查，区分本次新增失败、既有失败和环境阻碍；未运行的检查不写成通过。

向用户简洁说明结果、必要的设计取舍、实际验证及剩余问题。默认不安装检查工具、建设 CI、改写项目指令文件或调整发布配置；用户要求这些工作时再按当前授权实施。
